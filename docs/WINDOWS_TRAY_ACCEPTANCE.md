# Native Windows tray acceptance

Run these tools only in an owned interactive Windows test session. Stop the
existing Docking process first and use a fresh output directory for every run.
The tools create generated icons, bounded provider processes and owned windows;
they do not promote notification icons through registry edits or change user
notification settings. Explorer continues to render balloons.

CI collects both API matrices and both installed GTK profiles in fresh processes:

```sh
python -m tools.windows.ci --stage tray --installed-root artifacts/windows/runtime --wheel dist/docking.whl
```

Use the actual wheel filename. The batch writes `tray-domain.json` and all four
reports under `artifacts/windows/tray/`, validates them against the same release
requirements, and runs the remaining checks after a failure. Cancellation stops
the batch immediately. The workflow also runs this batch after an input failure
when the wheel was built successfully.

## Independent ABI and ownership matrix

```powershell
python -m tools.windows.visual.tray_provider_smoke --list
python -m tools.windows.visual.tray_provider_smoke --mode explorer --all --output artifacts/tray-explorer
python -m tools.windows.visual.tray_provider_smoke --mode backend --all --output artifacts/tray-backend
```

The independent C# provider uses public `Shell_NotifyIconA/W` and
`Shell_NotifyIconGetRect` calls, without importing Docking. The controller builds
actual x64 and x86 executables with the Windows .NET Framework compiler. Each
binary is reused by two independent PIDs so GUID path binding is identical.
The 40 cases combine both architectures, ANSI/Unicode, HWND/uID and GUID
identities, protocol versions 0/3/4 and valid native V1/V2/V3/full structure sizes.
V1 has no `uVersion`; V1/V2 cannot carry GUID identity.

Each case records API return values, native structure size, owner HWND/PID/uID,
raw callbacks, tooltip text and flag-only SHOWTIP changes. The second provider
attempts an ADD with the first provider's GUID, then a separate GUID-only MODIFY.
The ADD must preserve the original owner when rejected. The MODIFY phase records
metadata separately from the live callback recipient. Successful API calls do
not establish physical hover, keyboard, focus or visual acceptance.

Backend runs retain a bounded trace of owned packets: a 32-byte raw header,
total payload length, independently read canonical size/flags, decoded fields,
dispatch/forward results and post-dispatch item state. The prefix ends before
tooltip buffers; no unrelated providers or uninitialized tail bytes are retained.
The oracle requires exact raw/decoded flag agreement and checks Shell32's
source-size normalization: legacy V1/V2/V3 `cbSize` removes Vista-era SHOWTIP,
while the full structure preserves it. Requested flags and tooltip text must
remain correct in both cases. Canonical wire size alone cannot reveal the
original caller's structure size. Explorer mode records API acceptance without
claiming effective visible tooltip policy, which needs actual desktop input.

In backend mode the controller also observes Docking's projected state and copied
pixels, then closes every provider normally and verifies icon cleanup and shell
routing restoration. An unexpected provider exit, forced termination or failed
cleanup fails acceptance. `--installed-root path/to/site-packages` selects an
installed Docking implementation when the tool sources are staged separately.
Pair it with `--wheel path/to/docking.whl` for release acceptance. The shared
producer verifies every installed `docking/*` file against that exact wheel,
rejects missing/modified/unshipped files, and permits locally generated bytecode
caches. It emits `acceptance` with schema 1, implementation `installed-wheel`,
the verified wheel SHA256 and profile `api-matrix`. Source runs emit no installed
acceptance; Explorer remains an independent API comparison.

## Controlled Explorer comparison

```powershell
python -m tools.windows.visual.tray_provider_smoke --mode explorer --case 64-unicode-guid-v4-full --hold-phase fresh --hold-seconds 120 --output artifacts/tray-hover-fresh
```

Holds are available at `fresh`, `showtip-on`, `showtip-off`, `collision`,
`guid-modify` and `readded`. The first three occur **before any GUID-only request
or owner collision**, with SHOWTIP changes using the original nonzero HWND.
Use real pointer/keyboard input and capture the owned icon and rich popup at the
hold. A new run can repeat the same phase against `--mode backend`. Reach a newly
added Explorer icon through Win+B and the overflow UI; icons can initially be
hidden there. Do not infer a missing hover callback from a run that already
may have changed callback routing through a zero-HWND GUID-only modification.

The live provider journal contains `callback_sequence`, raw callback HWND/uID,
WPARAM/LPARAM, protocol version, native rich-popup visibility and foreground
readback. An external lab driver can issue revisioned `command-NNNNNN.json`
files under its owned `A`/`B` directories, following `command_revision` in
`state.json`. Commands include `rect`, `showtip` (`enabled` boolean), `balloon`,
`balloon-clear`, `menu`, `focus`, `hide`, `show`, `delete`, `add` and `snapshot`.
An optional `guid_only` boolean explicitly chooses zero HWND/uID; omit it during
fresh callback/policy checks. Create the case's `continue` file to end a hold.
The controller refuses to overwrite an unacknowledged command. Every provider
also stops at its bounded deadline, and an owned `stop` file requests normal exit.

## Full GTK and physical input

```powershell
python -m tools.windows.visual.tray_smoke --verify-geometry --verify-interactions --output artifacts/tray-gtk-v0-v4
python -m tools.windows.visual.tray_smoke --verify-interactions --legacy-version 3 --modern-version 4 --guid-only-updates --output artifacts/tray-gtk-v3-v4-guid
```

Add `--installed-root path/to/site-packages --wheel path/to/docking.whl` to
exercise a verified installed wheel with the source tools. Byte verification and
selection occur before the first Docking import; startup asserts the package,
application, tray backend/applet and Windows surface resolve inside that root.
`module_origins` records actual paths relative to the selected root, without a
private share prefix. Reports include the exact runtime options and an
`installed-wheel` acceptance profile of `gtk-v0-v4` or `gtk-v3-v4-guid`, bound to
the verified wheel hash. Omitting `--wheel` permits exploratory installed runs
without emitting release acceptance. The standalone generated-icon fixture
continues in its own bounded process.

This extends the existing native Python fixture and shared GTK smoke. It tests
real mouse motion and native rich-popup windows, standard GTK tooltip mapping,
SHOWTIP off/on/off without changing text, physical Enter/Space and Shift+F10,
raw callback UID/HWND and version-4 anchors. Version 0 keyboard activation uses
the documented legacy right-button sequence; versions 3/4 use `NIN_KEYSELECT`.
GTK focus selection is fixture setup; the actions are actual desktop events.

Interactive Windows tray panes use undecorated utility toplevel windows so GTK
can receive native keyboard focus. The surface backend selects this policy.
Passive provider hover preserves foreground ownership, and provider focus-return
requests still pass the claim and foreground checks before activating a pane.

Menu Escape must return both native HWND focus and GTK focus to the initiating
tray row. Read-only host dispatch observers verify that first, duplicate and
ineligible local `NIM_SETFOCUS` requests do not forward to Explorer. A physical
click on a window owned by a second provider PID makes a delayed return
ineligible; that request must leave foreground unchanged and the tray closed.
A request from the never-registered second provider must still reach Explorer.
Local attribution lasts up to five minutes while a provider interaction awaits
its return, then uses a fixed one-second grace for duplicates after completion
or invalidation. Later requests follow Explorer normally: this API carries no
action identifier that could distinguish a delayed duplicate from a new action.
Existing smoke phases cover actual pointer activation, double-click, native menu
selection, icon/pixel update, hidden state, deletion, re-add and normal shutdown.
`--restart-explorer` additionally exercises shell restart and icon handoff.

If the owned session permits banners, add `--notification-point X Y` at the
observed banner body. This requires actual SHOW, programmatic HIDE, physical
USERCLICK and natural TIMEOUT callbacks; it fails when policy suppresses the
banner. With no point, balloon acceptance is explicitly `not-run`, while the
provider remains available for controlled manual capture. No callback is
synthesized and no second balloon renderer is created.

Reports distinguish protocol-only observations, physical input assertions and
screenshots marked `captured-not-reviewed`. Review captured UI separately before
claiming visual acceptance. Preserve reports and captures as lab/CI artifacts,
not committed images. Unit tests run on other hosts with:

```sh
.venv/bin/python -m pytest tests/test_windows_tray_acceptance.py -q
```

[Shell_NotifyIcon](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw),
[NOTIFYICONDATA](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw),
[Shell_NotifyIconGetRect](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyicongetrect)
and [notification-area guidance](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area).
